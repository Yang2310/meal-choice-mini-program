# 系统架构与工程设计｜这顿有解

[English](architecture.md) | **简体中文** · [返回 README](../README.zh-CN.md)

## 1. 核心分层

微信原生小程序负责交互，页面通过业务服务、Repository 和 MediaService 访问数据，不直接耦合 MySQL 或 COS 的服务端细节。

```text
小程序页面（录入 / 美食库 / 店铺详情 / 抽选）
                   ↓
业务服务（菜品 / 店铺 / 筛选 / 抽选）
                   ↓
Repository 与 MediaService 适配层
                   ↓ HTTPS / JSON / 带身份的图片上传
Node.js / Fastify 后端 (/api/v1)
   ├─ 身份认证、数据权限和请求验证
   ├─ MySQL Repository、迁移、事务
   ├─ 腾讯 COS 私有媒体生命周期
   └─ 微信身份及内容安全接口
```

支持纯本地、API+MySQL、真实微信登录/文字审核、真实 COS 图片及 production 等环境模式，尽量让业务逻辑不依赖基础设施的差异。

## 2. 店铺与菜品的身份边界

**Store** 持有店名、地址、店铺整体评价以及可选类型；**Food** 持有菜品名称、状态、标签、分类、评分、价格、日期和媒体，与外食店铺关联。

当前在同一用户下，通过规范化店名判断 Store identity；已有店铺的冲突地址不能被静默覆盖。Store 类型独立于 Food 分类，且是可选的，不要求用户为了记录一道菜先完成复杂分类。

一个店铺可以关联多道菜，按店铺连续录入支持事务处理，避免只成功保存部分记录。

## 3. 三条独立抽选业务

**外食抽菜品、外食抽店铺、自己烧抽菜**分别使用各自的候选与筛选逻辑，避免不同模式的筛选状态互相干扰。

抽店铺支持依据店铺类型层级筛选，并排除同一轮已抽结果。业务抽选与揭晓动画分离，便于独立测试，而不是把抽选结果绑定在动画随机行为上。

## 4. 用户身份与私有图片

```text
wx.login → 服务端 code2Session → 内部用户 ID
    → 应用自己的 Session → 带身份的 REST API
    → 后端校验店铺/菜品/图片归属
```

图片访问路径：

```text
小程序图片预处理
    → 携带身份的 multipart 上传
    → 后端 MIME + 文件签名验证
    → 服务端生成 COS object key
    → 私有 COS 图片对象
    → MySQL 资源元数据
    → 详情页按需获取短期签名 URL
```

普通列表不必每次生成图片签名链接；客户端也不能任意指定存储 object key 或绕过用户权限。

## 5. 事务和失败边界

MySQL 与 COS 不能放进同一个 ACID 事务。店铺/菜品的批量创建在 MySQL 侧具备事务边界；后续创建失败时会清理已上传的 COS 对象。

删除时区分全部成功、**数据库完成但 COS 清理部分失败**，以及数据库操作失败，避免数据库删除后错误告知用户云端资源也全部清除。

## 6. 截图识别与图片审核是不同模块

**未来增强（尚未实现）：** 用户上传订单/团购页面截图，程序从截图中提取店名、已明确提供的地址、商品和菜品、数量、价格等客观信息，供用户校对并预填表单。目前没有确立模型供应商或实现期限。

**已有工程（生产回调尚待验收）：** 微信图片**内容安全审核**用于判断上传图片是否合规，涉及异步提交、状态跟踪和回调校验；它不会理解用户吃过哪些菜，也不会帮用户填写表单。

## 7. 部署与验收边界

目标生产方案为 Docker/Node/Fastify 后端、Nginx/HTTPS、托管 MySQL 和腾讯 COS。本地开发已有真实微信身份和图片服务联调。

私有文档记录了后端部署与冒烟验证，**但小程序仍未公开发布**；后端联调、生产环境配置、微信合法域名、真机验收及正式发布是不同层次的证据，不能混淆。

公开展示不会包含私有代码、真实用户数据、带签名媒体链接或生产密钥。
